# AI 棋力提升方案与通用评估流程

本文记录当前多数 meta 规则下的长期优化方向。当前规则、启发式实现、参数和新实验数据见 [`mcts_opt.md`](mcts_opt.md)；本文不保留已经废弃的规则或历史胜率数据。

## 当前实现

当前 AI 是纯 MCTS：选择阶段使用 `Q + U`，扩展阶段为合法动作创建等先验子节点，叶子阶段使用 tactical rollout 和多数规则启发式评估，最后按根子节点访问次数选择动作。当前没有策略网络、价值网络或开局库。

默认参数为：

| 入口 | n_playout | c_puct | rollout | limit |
| --- | ---: | ---: | --- | ---: |
| benchmark | 3000 | 0.3 | tactical | 32 |
| humanplay | 2000 | 0.3 | tactical | 32 |

默认规则是 `majority-utt-v1`：局部棋盘由三连线或局部平局决定状态，meta 只比较获胜局部棋盘的数量。平局局部棋盘不计入多数门槛；达到不可逆严格多数可以提前结束；所有局部棋盘结束后数量相同为和棋。meta 棋盘的排列不参与胜负。

## 主要限制

### 1. MCTS 先验没有动作知识

所有扩展动作的 `prior_p` 都是 `1.0`，因此 `c_puct` 只是探索常数，不是真正的策略先验。当前 tactical rollout 能提高叶子样本质量，但不能改变树扩展阶段的动作排序。继续微调 `c_puct` 容易在小样本上过拟合，应使用固定 seed 和独立局面集验证。

### 2. 启发式仍然是手工规则

当前叶子评估主要使用已赢局部棋盘数量差和未结束局部棋盘中的一连、两连威胁。它没有准确建模“走入哪个目标局部棋盘”对后续回合的影响，也没有对强制送入、自由落子和局部平局建立完整的价值模型。

### 3. Android 与 Python 的搜索生命周期不同

浏览器 humanplay 会保留 MCTS 对象并同步外部动作，Android 入口目前每次请求都创建新的 native MCTS 对象。相同单步时间下，Android 无法直接复用前一回合已经搜索的子树，产品端棋力不能只用 Python persistent-tree 数据推断。

### 4. 评估样本仍需扩大

空盘自对弈只能覆盖一类开局路径。正式比较还需要可达的早期、中局、残局和强制战术局面，并记录完整 W/D/L、seed、步数、耗时和异常。

## 后续优先级

### P2：提高同一时间内的有效搜索

- 用 profiler 区分 `clone()`、合法动作生成、局部状态计算和 rollout 的成本。
- 在保持状态正确性测试的前提下评估 move/undo 或更紧凑的状态复制。
- 评估稳定的动作排序、对称局面合并和 transposition table；哈希必须包含棋盘、当前玩家和 `next_board`。
- 为搜索加入根节点访问分布、Q 值、rollout 截止原因和每步耗时遥测。
- 在固定 playout 和固定毫秒两种预算下分别验证，不能只报告单次空盘 benchmark。

### P3：策略与价值模型

如果手工 tactical rollout 仍达到瓶颈，再考虑 AlphaZero 风格的策略/价值模型：

1. 状态编码必须包含双方落子、局部棋盘状态、当前玩家和 `next_board`。
2. 策略输出必须对非法动作做 mask。
3. 价值输出必须明确是当前玩家视角，并与 MCTS 反向传播的取反约定一致。
4. 模型候选必须在固定规则、固定预算和独立 seed 集上晋级。

## 评估合同

每轮实验运行前记录：

```text
规则版本：majority-utt-v1
代码版本：
构建类型与编译器：
机器/线程数：
候选配置：
参考配置：
预算：固定 playout 或固定毫秒
是否复用搜索树：
rollout / heuristic / model 版本：
seed 列表：
局面集版本：
```

正确性门禁必须先通过：所有动作合法、终局禁止继续落子、当前玩家和 `next_board` 一致、局部/ meta 状态一致、批量对局无死循环，并且固定 seed 能重放。规则或胜负定义变化时，必须创建新的基线并重新生成全部对局数据，不能与旧规则结果混合。
